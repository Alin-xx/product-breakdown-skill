01 · Summary

执行摘要

先给结论，再解释判断范围。读者在这里应能决定是否继续查看证据、架构或风险章节。

核心发现

已确认 描述一个由直接证据支持的关键产品事实。

已确认合理推断建议设计未知
02 · Evidence

证据与范围

记录材料、时间边界、不可访问项和证据等级，避免读者把报告当作官方内部实现说明。

证据 ID来源可确认事实等级
E01页面或源码位置保留可复核的原始信号已确认
E02多条证据组合说明推断链与不可见边界合理推断
03 · Domains

功能域

按用户可理解的能力域组织入口、核心动作、状态、资产和异常。

阅读提示

功能域不是代码目录的直接翻译；同一能力跨越多个层时要保留其端到端职责。

04 · End to end

端到端五流

在同一时间轴上对齐用户交互、Agent 控制、工具调用、数据上下文和资产流。

主流程与失败分支
flowchart LR
U[用户输入] --> W[工作台反馈]
W --> C{确认条件满足?}
C -- 是 --> X[执行与验证]
C -- 否 --> R[补充或修改]
R --> W
X --> O[结果与状态写回]

结论：主流程必须包含确认、执行验证和可见状态写回。

05 · Layers

分层架构

按九层检查，但只把有证据或清晰设计理由的组件放入主图。

06 · Relations

Agent、工具与交接

列清输入、判断、工具、输出、上下文读写、完成条件与失败处理。

07 · Context

全局上下文与数据流

区分事实字段、语义化推导字段和建议字段，并检查版本、引用与失效规则。

08 · Knowledge

知识与公共资产

区分产品知识、项目数据、公共素材、用户私有资产和反馈数据。

09 · Models

模型接入与路由

页面只出现单一模型时，不推断完整的动态路由或供应商策略。

10 · Technology

技术选型判断

采用“需要能力 → 可能类别 → 推荐方案 → 不能确认原因”的结构。

11 · Entities

数据实体与 ER

实体名是分析模型，不冒充真实数据库表名。

核心实体关系
erDiagram
USER ||--o{ PROJECT : owns
PROJECT ||--o{ WORKFLOW : runs
WORKFLOW ||--o{ TASK : contains
TASK ||--o{ TOOL_CALL : invokes
PROJECT ||--o{ ASSET : produces

结论：项目、工作流、任务、工具调用和资产需要稳定引用与版本关系。

12 · Sequence

核心时序

时序图区分确认、执行、验证、失败、重试和状态写回。

一次任务执行
sequenceDiagram
actor U as 用户
participant W as 工作台
participant A as Agent/协调器
participant T as 工具
U->>W: 提交需求
W->>A: 建立任务上下文
A-->>W: 请求确认
U->>W: 确认
W->>A: 执行
A->>T: 调用
T-->>A: 结果或错误
A-->>W: 验证并写回状态

结论：完成不能只由最终消息确认，还需结果和状态信号。

13 · Panorama

产品全景图

全景图展示层与关键关系；高密度字段仍回到表格阅读。

14 · As-Is

当前可见实现

已确认 与 合理推断 分开呈现，不混入理想方案。

15 · To-Be

建议设计

建议设计 说明触发条件、架构措施、预期效果和优先级。

16 · Risks

风险

风险需要触发条件、影响、当前控制、建议控制和证据，而不是泛化警告。

风险 示例风险

当聊天完成文案与任务状态冲突时，用户可能误认为资产已经可用；建议以状态与资产交叉验证。

17 · Traceability

架构组件追溯

为主图中的组件记录“为什么需要、由什么证据支持、属于何种等级”。

18 · Unknowns

未知与验证清单

未知 证据不足的结论保留为问题，并给出最小验证方式。
