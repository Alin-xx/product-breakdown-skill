## 1. 通用准备

1. 列出全部输入材料和不可访问项。
2. 建立证据清单与编号；原文件不改名、不覆盖。
3. 按时间重建用户动作、页面反馈、资产变化和状态变化。
4. 记录按钮、表单、Agent 名、卡片、任务、错误、预览/导出入口。
5. 单列冲突：聊天↔任务、聊天↔画布、画布↔资产库、工具结果↔状态。
6. 选择当前任务模式，只加载对应报告 schema；需要 HTML 时再加载生产流水线与视觉系统。

## 2. 用户旅程模式

### 取证顺序

1. 用户最初提交：原始需求、剧本、风格、参考资料、上传素材。
2. 产品第一次回应：Agent 名、规划摘要、表单和按钮。
3. 每次确认：用户决定、页面新增/修改、资产/状态变化。
4. 修改入口：不满意、卡片编辑、返回前一步、删除或重新选择。
5. 失败/中断：生成失败、余额不足、安全拦截、中断、重试和后续操作。
6. 输出阶段：预览、剪辑、下载、发布、完整性警告。

### 交付顺序

1. 查看范围。
2. 无法访问或确认的证据。
3. 用户旅程证据表。
4. 三泳道用户旅程图。
5. 情绪、想法、痛点、可补充项和产品机会。
6. 三个最值得讨论的体验问题。

旅程证据表字段：阶段、用户目标、用户动作、页面反馈、用户决定、页面/资产状态变化、问题或阻力、证据。

图只保留：用户、产品界面、系统结果。判断节点使用菱形，分支必须有条件，如“满意/不满意”“成功/失败”“余额充足/不足”“继续/中断”。

停止：交付后等待确认，不进入 Agent 调用拆解。

## 3. Agent 契约模式

### Agent 识别

- 按加入时间列出名称、触发者、接替者、下游、是否重调。
- 不预设 Agent 数量。
- UI 容器、任务标签和业务 Agent 分开。
- “通常应存在但未出现”的 Agent 只作为缺口，不补进清单。

### 每个 Agent 的六类输入

1. 用户当前输入。
2. 用户长期信息。
3. 项目全局上下文。
4. 上游 Agent 输出。
5. 平台公共资产/知识/规则。
6. 工具与运行时结果。

### 每个 Agent 的契约

依次写核心目标、触发条件、输入、可观察判断、工具、输出、上下文读写、完成条件、异常重试和尚未确认问题。

工具名未知时使用“读取项目上下文”“生成角色主图”等功能命名，并标注非官方工具名。计划公开不等于工具已执行。

### 交付顺序

范围/缺口→Agent 清单→I/O 契约卡→工具总表→上下文字段→生产者—消费者→Agent 流程图→事实/推断/未知→五个验证问题。

停止：等待用户核对，不编写完整 System Prompt。

## 4. 单 Agent Prompt 模式

只处理用户指定 Agent；完整收集它在当前 Space 中的全部记录。

### 先回答边界

问题、接管时间、触发者、下游、允许/禁止工作、修改重触发、停止、自动继续、是否等待确认。

### 契约与状态机

- 输入：沿用六类来源，区分必填/可选。
- 输出：用户回复、页面组件、结构化字段、媒体资产、状态、下游任务。
- 工具：前置确认、成功验证、失败/重试、重复扣费、用户中断、状态写入失败。
- 状态：waiting_input、planning、waiting_confirm、executing、validating、completed、failed、interrupted、retrying、handoff；按证据调整。

### 功能等价 System Prompt

使用 15 节：Agent 名称、角色、核心目标、任务边界、输入契约、全局上下文协议、工作流程、工具调用规范、用户确认、结果验证、修改回退、异常处理、状态机、下游交接、完成条件、输出格式。

Prompt 必须可直接使用，但声明“功能等价，不是官方原文”。尖括号工具为占位符。字段不存在真实名称时标注语义化推导设计。

### 测试集

至少覆盖：正常完整、缺必要输入、局部修改、工具失败、用户中断、页面/上下文冲突。推荐再加重复请求和下游不可用。

停止：只交付该 Agent，不拆其他 Agent。

## 5. 完整产品架构模式

### 事实来源与功能域

列用户操作、聊天、Agent、组件、画布、版本、模型、工具结果、错误、计费、官方资料。检查账号权限、入口、项目、剧本、风格、角色/Face ID、场景、道具、分镜、视频、音频/音色、预览/剪辑、版本、资产库、发布、计费、错误任务、安全和质量。

### 五条流

在同一端到端表中写用户交互、Agent 控制、工具调用、数据/全局上下文和媒体资产。每步包含触发、处理、读取、判断、工具、结果、状态写回、确认、交接和失败分支。

### 九层架构

1. 用户与渠道。
2. 交互与工作台。
3. 产品应用。
4. Agent 与流程编排。
5. 工具与服务。
6. 模型接入与路由。
7. 全局上下文与数据。
8. 知识与公共资产。
9. 基础设施与治理。

不要预设每层已确认。主控 Agent 不可见时，可画“工作流/状态协调器【合理推断】”，不要虚构额外业务 Agent。

### 上下文、知识、模型和底层

- 使用 report-schemas 中的上下文模块作为分析模板，不冒充真实字段。
- 区分项目数据、公共知识、公共资产、用户私有资产和反馈数据。
- 页面只出现一个模型时，不推断完整动态路由。
- 按“需要能力→可能选型类别→推荐方案→不能确认原因”写底层选型，不猜厂商。

### 实体与图

检查实体模板并输出 Mermaid ER、sequenceDiagram 和九层全景 flowchart。主图标注调用、读取、写入、事件、确认、资产引用、状态更新；实线=已确认，虚线=合理推断，点线/特殊色=建议设计；风险节点显式标红。

### 交付顺序

执行摘要→证据/缺口→功能域→端到端→分层→Agent/工具/上下文→上下文→知识→模型→选型→实体/ER→时序→全景图→As-Is→To-Be→风险→追溯→未知。

## 6. 多产品对比模式

### 比较前置条件

- 每个对象有明确版本或时间快照；无法对齐时在标题区提示。
- 每个对象的材料类型和证据强度可说明；一方只有营销页、另一方有完整源码时，不把证据量差异写成能力差异。
- 先建立共同问题清单，再读取单产品结论。至少检查：定位、核心抽象、用户流程、Agent/工具、扩展方式、状态与持久化、上下文、协议、安全治理、适用场景、风险和未知。

### 比较方法

1. 为每个共同问题分别提取 A、B 的证据和边界。
2. 写“结构差异 → 带来的行为影响 → 在什么目标下更合适”，不直接排总名次。
3. 共同点和共同风险单列；无法公平对照的内容进入“不可比项”。
4. 所有结论回链到原报告或原始证据，必要时标注不同快照。
5. 如需融合方案，明确它属于【建议设计】，并说明取自各对象的哪种能力。

### 交付顺序

比较范围与证据对称性 → 一句话差异 → 同维度对比 → 关键架构差异 → 共同点 → 不可比项 → 场景化选型 → 融合建议 → 共同风险 → 证据入口与未知。

停止：完成对比报告后停止，不自动修改两份单产品报告；发现原报告证据错误时先报告，再由用户决定是否回修。

## 7. 证据复核模式

只检查：事实标签是否有直接证据；推断是否由事实支持；计划是否误写成调用；冲突是否保留；主图是否混入无证据且无设计理由的组件；证据编号、链接和原文是否准确。

不要新增产品架构，除非用户明确要求修订。

## 8. 停止点

- 用户旅程完成：等待确认。
- Agent 契约完成：等待确认。
- 单 Agent Prompt 完成：等待确认。
- 完整架构完成：停止，不继续猜技术栈或官方 Prompt。
- 多产品对比完成：停止，不把选型建议扩展成实施或迁移计划。
- 浏览器遇到权限/安全限制：记录缺口，使用用户已提供的本地材料；不绕过限制。
