# 报告生产流水线

本文件把“产品拆解”与“可交付 HTML”串成同一条流水线。执行完整产品架构、对比报告或用户明确要求成品 HTML 时读取；只做证据复核时无需读取。

## 1. 输入盘点与输出约定

先确认：分析对象、材料范围、截止快照、报告类型、读者、文件位置、是否允许联网和是否需要对比。保留原材料，不覆盖截图、源码或已有报告。

把交付拆成三层：

1. **事实层**：证据索引、原文、源码位置、页面状态和时间边界。
2. **分析层**：用户旅程、功能域、Agent/工具/上下文、架构、风险和结论。
3. **呈现层**：信息层级、视觉语义、导航、图表、响应式、暗色和打印样式。

呈现层可以提高可读性，但不得改变事实等级、隐藏冲突或把建议包装成现状。

## 2. 先写内容模型

在写 HTML 前完成结构化提纲：

- 报告标题、副标题、快照日期、证据范围；
- 一句话结论和 3–5 条最重要发现；
- 章节及稳定 `id`；
- 证据 ID 与章节的映射；
- 需要用表格表达的字段；
- 需要用图表达的关系；
- 未知、风险和后续验证问题。

每张图先写一句“这张图要证明什么”。如果表格已经能清楚回答，就不再添加图。

## 3. 选择报告形态

### 单产品架构报告

使用一个产品主色，状态色仅表达证据等级和风险。首页突出产品定位、架构特征、证据快照和结论，不做营销式大 Hero。

推荐叙事：摘要 → 证据 → 功能与五流 → 分层架构 → Agent/工具/上下文 → 数据实体与图 → As-Is/To-Be → 风险与未知。

### 双产品或多产品对比

每个对象使用稳定且等权的识别色；“优劣、推荐、风险”使用独立语义，不借用任一对象的品牌色。所有关键结论必须回链到各自报告或共同证据。

推荐叙事：比较范围 → 一句话差异 → 同维度对照 → 共同点/分歧 → 场景化选型 → 融合建议 → 共同风险 → 证据入口。

不要把对比写成两个摘要拼接。每一行比较都回答同一问题，无法等维比较的内容放入“不可比项”。

## 4. 低保真后再视觉化

先用文本或 ASCII 确认阅读路径，再套用视觉系统。默认路径：

```text
[标题 / 范围 / 快照]
[关键结论与证据图例]
[章节导航]
├─ 分析章节
│  ├─ 结论句
│  ├─ 表格或关系图
│  └─ 证据与未知
└─ 风险 / 后续验证 / 方法说明
```

视觉实现前读取 [html-visual-system.md](html-visual-system.md)。从 [../assets/report-template.html](../assets/report-template.html) 复制结构和设计令牌，按产品语义调整主色与密度，不复制示例文案。

## 5. 实现 HTML

- 生成完整、自包含的 UTF-8 HTML；CSS 和必要的轻量交互内联。
- 默认不依赖外部字体。Mermaid 可按用户环境决定使用 CDN，但必须保留源码和失败时可读的文本结论。
- 所有章节使用稳定 `id`；目录链接与标题一致。
- 表格放入横向滚动容器；代码、证据 ID 和提交哈希使用等宽字体。
- 外部和源码证据优先链接到固定版本；本地证据链接必须相对报告文件解析成功。
- 交互只用于导航、折叠、复制和主题等展示动作，不发送数据。

## 6. 三轮验收

### 内容验收

检查事实等级、结论—证据追溯、同一时间边界、未知项、冲突项和报告类型对应的必需章节。

### 自动验收

运行：

```bash
python3 scripts/validate_html_report.py /absolute/path/report.html --profile architecture --quality visual
```

对比报告使用 `--profile comparison`。修复错误后再进入视觉验收。

### 视觉验收

在浏览器查看至少：

- 桌面宽屏约 1440×900；
- 手机窄屏约 390×844；
- 长表格、长链接、长标题和 Mermaid 图；
- 系统暗色模式（若报告声明支持）；
- 打印预览或导出 PDF（若交付需要）。

重点检查：首屏能否说明“对象、范围、结论”；正文是否出现大段等权卡片；导航是否遮挡锚点；除表格/图之外是否横向溢出；语义是否仅依赖颜色；打印时导航和交互控件是否隐藏。

无法完成浏览器或打印验收时必须明确说明，不得以自动校验替代视觉结论。

## 7. 交付

最终回复给出 HTML 的绝对可点击路径，并说明：报告类型、证据快照、自动校验结果、已检查的视口，以及仍需用户决定的未知项。只有在用户明确要求时才部署或发布。
